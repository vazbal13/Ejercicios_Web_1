  • Cuando afronto un problema, ¿hago todo lo que está en mi mano para solucionarlo? Asegúrate de que hayas hecho un esfuerzo suficiente tratando de arreglarlo por ti mismo antes de pedirle ayuda a alguien.
  • ¿Me estoy complicando demasiado? Si te bloqueas con algún problema, piensa que podría haber una solución simple que ya se ha intentado y probado.
  • ¿Es satisfactorio? ¿Te sientes satisfecho cuando solucionas un problema o terminas un trabajo? Si no, intenta y piensa en maneras de cambiarlo. ¡Cada victoria cuenta!

    Organización de CSS: el problema de los nombres

  • Cuando empiezas con proyectos pequeños, escribir CSS parece fácil. Pero a medida que el código crece, mantenerlo ordenado se vuelve complicado. Sin una estructura clara y buenas reglas de nombres, el CSS se desorganiza rápido: aparecen conflictos, el mantenimiento se dificulta y el código se vuelve frágil.
  • Aquí es donde entran en juego las metodologías CSS. Su objetivo es proporcionar pautas y mejores prácticas para escribir código que sea limpio y fácil de mantener, sin importar cuánto crezca el proyecto.

    • 1. El conflicto de estilos

  • CSS tiene una característica que puede ser peligrosa si no se controla: todos los estilos son globales. Imagina este escenario: estás creando un elemento de "Login" y decides crear una clase .button para tu botón azul y darle un estilo background-color: blue. Unos días después, estás trabajando en la sección de "Contacto" y necesitas un botón diferente, tal vez verde. Como el nombre .button es muy común y lógico, es probable que tú (o un colega tuyo) intenten usar ese mismo nombre de clase .button de nuevo al final de tu hoja de estilos (o incluso en otro archivo CSS conectado al mismo HTML), pensando en este nuevo botón, pero ya con background-color: green .
  • ¿Por qué ocurre esto? Los navegadores leen el código CSS de arriba abajo y solo aplican los estilos después de haber leído toda la hoja de estilo. Esto quiere decir que las reglas que estén escritas cerca del final del documento anularán a las que están más cerca de su comienzo. Por lo tanto, si tienes dos estilos que se contradicen entre sí, tendrá prioridad el que aparezca en último lugar: el nuevo estilo .button (verde) sobrescribirá al anterior. Tu botón de "Login", que debería ser azul, ahora se volverá verde también. Al intentar crear algo nuevo, sin querer has roto lo que ya funcionaba. Esto se vuelve una pesadilla en proyectos grandes: cambias una línea de código en un lugar y rompes el diseño en otro lugar que ni siquiera estabas mirandos

    • 2. La trampa de la especificidad

  • Imagina que te das cuenta del error. Quieres que el botón de “Login” vuelva a ser azul, pero no quieres borrar el código de abajo. Se puede recurrir a una solución desesperada: escribir selectores muy largos y complejos para "forzar" al navegador a aplicar el color azul, ganándole a la regla verde por fuerza bruta. Esto se conoce como "guerras de especificidad". El resultado puede verse así:
  • No es el mejor código, ¿verdad? Cuando un desarrollador nuevo se incorpora al equipo, pasará más tiempo intentando descifrar qué hace ese código que trabajando en él. Además, es un código muy frágil: si cambias mínimamente el HTML (por ejemplo, quitas el h1 o el div), el selector dejará de funcionar y el botón se volverá verde otra vez.

    • 3. El problema de la mantenibilidad

  • Entonces, ¿qué podemos hacer para evitar esto? La respuesta lógica es que necesitamos elegir un nombre de clase único para cada botón, de modo que no entren en conflicto. ¿Pero cómo los llamaremos? ¿.blue-button y .green-button?
  • Además de los conflictos técnicos, existe otro problema grave: la dificultad para mantener el código a largo plazo. Nombres confusos pueden convertir un cambio de diseño de 5 minutos en una tarea de varias horas. El problema con nombres como .blue-button es que describen cómo se ve el elemento hoy, pero no para qué sirve. Imagina este escenario: has usado la clase .blue-button en 50 páginas diferentes de tu sitio. Mañana, el equipo de diseño decide cambiar la imagen de marca y dice: "El azul ya no está de moda. Ahora todos nuestros botones principales deben ser naranjas". Te encontrarás con un dilema absurdo: o cambias el CSS para que .blue-button tenga un fondo naranja (creando una clase que "miente" y confunde a cualquiera que lea el código), o decides cambiar el nombre a .orange-button, lo que te obligará a buscar y reemplazar manualmente ese nombre en todos los archivos HTML.

    • Conclusión

  • Para evitar este caos de conflictos, selectores complejos y nombres confusos, los desarrolladores han creado metodologías. Es parecido al tráfico: si cada persona conduce como quiere, todo se vuelve un desorden. Pero cuando todos siguen las mismas señales, todo fluye mucho mejor. En el desarrollo web existen varias metodologías populares para poner orden. En la próxima lección, veremos qué son exactamente, en qué se diferencian y cuál te recomendamos utilizar para empezar tu camino en el desarrollo profesional.

Metodologías CSS Aprendimos que una metodología es simplemente un acuerdo de equipo para escribir código ordenado y escalable. Exploramos dos enfoques principales: BEM (basado en componentes independientes) y Utility-first (basado en clases pequeñas para estilos visuales). Aunque ambos son válidos, te recomendamos empezar con BEM porque te entrena a pensar en bloques reutilizables, una habilidad esencial para el futuro. Recuerda su sintaxis clave: Bloque: .nav (el componente independiente). Elemento: .nav__item (se conecta con dos guiones bajos __). Modificador: Define una variación y se conecta con un guion bajo _. Puede ser de dos tipos: Booleano: .nav__item_active (para estados simples de sí/no). Clave-valor: .nav_theme_dark (para opciones múltiples como temas o tamaños). Esta estructura hace que tu código sea predecible y fácil de mantener.     • ¿Qué es linea de comandos?

  • Comencemos a explorar la línea de comandos explicando parte de la terminología. Como dijimos en la lección de introducción, la línea de comandos es una interfaz basada en texto para interactuar con una computadora. Podemos acceder a esta interfaz a través de programas llamados terminales o emuladores de terminal. Más específicamente, el emulador de terminal interactúa con un shell, un programa que interpreta las entradas de la línea de comandos y las traduce en instrucciones para el sistema operativo. Los programas shell más comunes en macOS y Linux son bash y zsh, los cuales comparten interfaces similares, así que sus comandos, normalmente, son interoperables. Al emulador de terminal predeterminado en estos sistemas se le conoce, simplemente, como Terminal. Pero, los programas shell y terminal predeterminados en Windows son muy distintos de bash y zsh. Es por ello que tuviste que instalar Git en la lección anterior. Para los usuarios de Windows, Git Bash ya viene incluido en Git, lo que proporciona un shell bash y un emulador de terminal en Windows. Abrir la terminal Ahora, manos a la obra.     • Autenticar tu cuenta con SSH

  • ¿Qué es el SSH? Cuando dos computadoras se comunican entre sí necesitan una forma segura de enviarse información. Si envían los datos sin protección cualquier persona podría interceptarlos y leerlos, igual que si hablaras desde tu ventana y alguien en la calle escuchara la conversación. SSH es una manera de evitar que eso pase. Imagina que tú y tu amigo tienen un código secreto que solo ustedes entienden. Puedes escribir tu mensaje en ese código, pasárselo y nadie más podrá entenderlo aunque lo vea. SSH funciona igual. Protege la información convirtiéndola en algo que solo los equipos autorizados pueden descifrar. Para lograrlo SSH usa dos claves que trabajan juntas: una clave pública y una clave privada. La clave pública es como un candado que cualquiera puede tener. La clave privada es la llave que solo tú guardas. Cuando ambas coinciden la comunicación se abre y la información viaja segura. En nuestro caso usamos SSH para conectarnos a GitHub de forma segura. Así tu computadora puede enviar código al repositorio sin pedirte tu usuario y contraseña en cada acción y sin exponer tus datos. Más adelante también lo usarás para trabajar con servidores remotos pero por ahora solo necesitas entender que SSH es un método seguro y conveniente para verificar tu identidad.

    • Ignorar archivos con .gitignore

  • A estas alturas, ya sabes cómo rastrear los cambios que se han hecho en los archivos de un proyecto a través de Git, y empujarlos a la nube con GitHub. Sin embargo, hay algunos archivos que no deben comprobarse en el control de versiones. A veces, esto se debe a que el archivo contiene secretos, como claves API o contraseñas. Definitivamente, ¡no quieres empujar eso a GitHub! Otras veces, podrías no querer rastrear los cambios en un archivo simplemente porque no lo necesitas. Por ejemplo, la mayoría de proyectos se someten a varios tipos de optimización antes de ser empujados a producción. Estas optimizaciones las llevan a cabo herramientas automatizadas, las cuales transforman el código fuente de un proyecto, pasando de algo con lo que los seres humanos trabajan fácilmente a algo que tendrá un mejor desempeño en producción. Normalmente, este código optimizado no se comprobará en el control de versiones, ya que puedes construirlo de nuevo desde el código fuente. Y también están los archivos .DS_Store (Desktop Service Store, o "Almacén de servicios de escritorio", en español). Estos son archivos ocultos que macOS crea cada vez que echas un vistazo dentro de una carpeta mediante el explorador de archivos predeterminado de la GUI. No hay por qué comprobar estos archivos en el control de versiones, y hacerlo podría incluso ser un riesgo de seguridad (en inglés). Así que, ¿cómo lo resolvemos? Con un pequeño archivo llamado .gitignore.

    • Conclusión: el flujo de trabajo de Git/GitHub

    Trabajando localmente, siempre seguirás los siguientes cuatro pasos: Los cambios se hacen a un archivo o varios archivos. Los archivos se agregan al área de staging con git add. Los cambios se confirman con git commit. Repite los pasos 1-3 siempre que sea necesario. Interactuar con GitHub agrega unas tareas más a nuestro flujo: Se descargan los últimos cambios con git pull (para asegurarte de estar al día). Se hacen los cambios en uno o varios archivos. Los archivos se agregan al área de staging con git add. Los cambios se confirman con git commit. Se repiten los pasos 1-4 siempre que sea necesario. Los commits se empujan a GitHub con git push. Se repiten los pasos 1-6 siempre que sea necesario.

    • Formatear el código con Prettier y Editorconfig

  • los formateadores automáticos de código. Formatear tu código podría parecer algo menor, la cereza en el pastel, pero es algo crucial. Un formateo consistente garantiza que tu código sea legible, tanto para ti como para los demás, incluyendo tu tutor, equipos de revisión de código y tus futuros colegas. Además, escribir código limpio y consistente es vital, y hasta las compañías han acordado que los desarrolladores deben apegarse a instrucciones específicas de estilo del código. El formateo consistente también te ayudará a escribir tu código, ya que te será mucho más fácil detectar errores de sintaxis, incluso antes de que se conviertan en errores en tu página web. Uno de los principales retos del formateo es la indentación consistente, especialmente con un lenguaje fuertemente anidado como HTML. Podría llevarte algo de tiempo repasar todo tu marcado para que la indentación de tu código sea perfecta. Pero afortunadamente, no tienes que hacerlo. Existen algunas herramientas que lo pueden hacer por ti.

    • Editorconfig

  • es un formato de configuración que funciona con la mayoría de los editores de código. Un caso de uso particular es establecer tu estilo de indentar. Por defecto, VS Code utiliza cuatro espacios para su indentación. Sin embargo, el estándar que muchas empresas tecnológicas siguen hoy es utilizar dos espacios para la indentación, ya que hace tu código más compacto. Puedes configurar tu editor para indentar dos espacios con Editorconfig. Para ver las instrucciones de instalación y uso, puedes usar el botón de activación.

    • Prettier

  • es un "formateador de código obstinado" para HTML, CSS y JavaScript. Prettier contiene un conjunto de reglas de formateo predeterminadas, así que puedes usarlo con una instalación y configuración mínimas. Es muy bueno haciendo lo que hace, y se emplea mucho entre profesionales de desarrollo web; así que utilizarlo para formatear tu código es un requisito en todos tus proyectos en TripleTen.
